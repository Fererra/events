# Навантажувальне тестування API (`k6`, вимога N2 / ES-41)

Перевірка нефункціональної вимоги **N2** (ЛР1 §4): *95% запитів до API повинні оброблятися за час не більше ніж 300 мс за навантаження до 50 запитів на секунду*.

Скрипт: [tests/load/k6-api-load.js](../tests/load/k6-api-load.js).

---

## 1. Конфігурація стенду та профіль навантаження

- **Стенд:** повний Docker Compose (`web` Nginx 1.27 TLS 1.2/1.3 → `app` Node.js 22 / Fastify 5, `DB_POOL_MAX=10` → `postgres` PostgreSQL 17).
- **Інструмент:** `grafana/k6` (запуск у мережі `event-service_default` через HTTPS `https://web/api`).
- **Фаза `setup()`:** створення стартової локації (`capacity: 15000`), 3 активних подій із квитками (`limit: 4000`) та пулу з 20 автентифікованих користувачів (щоб під час 30-секундного заміру вимірювати саме ендпоінти каталогу й реєстрації без навмисної OWASP-затримки Argon2id у `/auth/login`).
- **Профіль навантаження (`constant-arrival-rate`, тривалість `30s`):**
  - `catalog_read`: `20 iters/s` × 2 запити (`GET /api/events?page=1&limit=10&status=ACTIVE` + `GET /api/events/:id/tickets`) = **40 RPS** читання;
  - `event_registration`: `15 iters/s` (`POST /api/events/:eventId/registrations`) = **15 RPS** транзакційного запису з `SELECT … FOR UPDATE` та асинхронною проекцією в `event_stats`.
  - Сумарне цільове навантаження: **55 RPS** (із запасом понад вимогу `50 RPS`).

---

## 2. Запуск

```bash
# 1. Підняти повний стек (якщо ще не запущено)
docker compose up -d --build --wait

# 2. Запустити k6 через Docker (без локального встановлення k6)
docker run --rm --network event-service_default \
  -e BASE_URL=https://web/api \
  -v "$PWD/tests/load:/scripts:ro" \
  grafana/k6 run /scripts/k6-api-load.js
```

Локально зі встановленим `k6`: `BASE_URL=https://localhost:8443/api k6 run tests/load/k6-api-load.js`.

## 4. Аналіз вузьких місць та рекомендації

За цільового навантаження `55 RPS` система працює із **25-кратним запасом** щодо SLA `300 мс` (`p95 = 11.89 мс`), оскільки побічне оновлення статистики (`EventStatsProjector`) винесене за межі HTTP-відповіді через `afterCommit` (вимога **N5**), а запити до PostgreSQL покриті індексами (`events_status_ends_at_idx`, `ticket_types_event_id_idx`, `registrations_ticket_type_status_idx`).

Потенційні вузькі місця при масштабуванні вище цільового профілю (рекомендації для подальшого розвитку):

1. **Конкуренція за один «гарячий» рядок `ticket_types` (`SELECT … FOR UPDATE`):** при піковому напливі сотень запитів/с на *один* конкретний тип квитка транзакції серіалізуються на рядковому блокуванні, а пул з'єднань (`DB_POOL_MAX=10`) може насичуватися. При масштабуванні варто збільшити `DB_POOL_MAX` і задати `statement_timeout` / `lock_timeout`.
2. **CPU-ємність Argon2id на `/api/auth/register` та `/api/auth/login`:** параметри OWASP (`m=19 MiB, t=2`) навмисно навантажують CPU для захисту від перебору. У `docker/web/nginx.conf` доцільно додати `limit_req_zone` (rate limiting) для `/api/auth/*`, щоб запобігти DoS через масові спроби входу.
3. **Запит `count(*)` при пагінації `GET /api/events`:** на великих таблицях (десятки тисяч подій) `count(*)` разом із `offset` лінійно сповільнюється; у майбутньому варто перейти на keyset-пагінацію (`cursor`).
